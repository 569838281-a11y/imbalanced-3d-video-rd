四、相较「初始代码」训练更慢的原因（重要）
--------------------------------------------------------------------------------
  此处「初始代码」指：experiment=non_rd_vs_rd/resnet3d + 原 ModelModule，
  在相同数据与 batch_size=4 下，日志约 0.25 it/s、单 epoch 约 60–65 分钟；
  当前 decoupled + erdes_gpu 实测约 0.30 step/s（~3.3 s/step），单 epoch 相近或略慢。
  若感觉「明显更慢」，通常来自以下叠加因素：

  【1】数据路径：每 step 现场解码 mp4（主因，与是否 decoupled 无关）
      • VideoDataset + PyAV：每个样本读盘、解码最多 160 帧、再采样 96 帧。
      • 训练集 3873 条 → batch=4 → 每 epoch 969 step；解码占大部分时间，GPU 常空等。
      • 第二次更改提供的 D 盘 .pt 缓存（resnet3d_decoupled_fast）未构建时，无法加速。
      • 初始 resnet3d 同样在线解码，故单 epoch 量级相同；未使用缓存则不会比初始快。

  【2】第三次：defer_resize + GPU 预处理（额外开销）
      • 初始代码在 CPU 的 Dataset 内完成 pad + trilinear resize（utils.resize）。
      • 现改为 CPU 只解码，batch 内 pad 对齐（pad_video_batch_collate），再在 GPU 做
        trilinear resize（gpu_video_ops）。多一次 GPU 上逐样本 interpolate，且 batch
        内分辨率不一致时无法完全向量化，略增每 step 时间。
      • 收益是减轻 CPU 算力占用，但瓶颈仍在 PyAV，整体 epoch 时间不会缩短。

  【3】DataLoader 与进程
      • num_workers=2（配置）时实际可能出现多个 worker 子进程，RAM ~9GB。
      • persistent_workers、pin_memory 有利于稳定，但子进程同时抢磁盘读 mp4。
      • 曾同时运行两个 train.py，显存/磁盘争抢会使观感「卡死」；已按第三次要求改为单进程。

  【4】解耦方法本身的计算（相对初始 ModelModule 略增）
      • Mixup（阶段一）、阶段二 Logit Adjustment、更多 val 指标（含 PR-AUC）。
      • 相对解码可忽略，但每 step 前向/反向略重于纯 BCE ResNet3D。

  【5】日志与观感（不等于算得慢）
      • 早期关闭 rich 进度条 + 管道缓冲 → 长时间无输出，误以为卡住。
      • 第三次已加 TrainingProgressCallback 与 PYTHONUNBUFFERED。

  【6】与「15 epoch 就跑完」的初始 run 对比
      • 初始 resnet3d 在 epoch 16 因 CPU OOM 中断前，已完成 15 个完整 epoch（约 15×65 min）。
      • 当前 decoupled 若跑满 15 epoch，总墙钟时间量级相近（~14–15 h），并非算法多训 50 轮。

  【如何接近初始速度或更快】
      • 构建缓存：python scripts/build_video_cache.py --split all
      • 训练：experiment=non_rd_vs_rd/resnet3d_decoupled_fast（目标 ~10 min/epoch）
      • 或继续用 resnet3d（非解耦）且保持 batch=4、单进程、避免双开训练。
